Purpose of this ADR
-------------------
This ADR records the technical direction discussed for MIMIR without inventing
product commitments, organisational requirements, service-level objectives, or
security policies that have not been specified.

MIMIR is intended to be a locally hosted operations-investigation assistant. It
is not primarily a coding agent. Its main purpose is to make terminal-based
on-call work, repository investigation, command construction, container
inspection, and evidence-backed diagnosis easier.

The target execution environment is the user's primary Apple Silicon Mac with
128 GB unified memory. The system must also be usable from:

1. A local computer CLI.
2. A local or remotely reachable web interface.
3. Eventually, Warp through a custom authenticated OpenAI-compatible inference
   endpoint configured as a custom BYOK/custom inference endpoint.

Coding work will continue to be handled primarily by existing company-provided
GLM access through LiteLLM and by Claude/Codex subscriptions. MIMIR may inspect
code and explain repository behaviour, but code generation and autonomous code
modification are not its primary design goal.

-------------------------------------------------------------------------------

1. Context
==========

The current tooling landscape provides strong hosted coding agents, but the
desired on-call workflow is more terminal-centric and environment-specific.

The user needs an assistant that can help with tasks including:

- Searching repositories.
- Finding patterns across files for a particular service or execution flow.
- Determining whether a feature, fallback, configuration, or behaviour exists.
- Explaining where that behaviour is implemented and what evidence supports the
  conclusion.
- Constructing kubectl commands.
- Viewing and analysing kubectl command output.
- Inspecting logs and containers through SDM.
- Investigating Kannel and Tankers environments and containers through existing
  local access.
- Constructing psql or other operational commands where appropriate.
- Explaining service timeouts from logs, deployment state, configuration, and
  repository evidence.
- Suggesting commands directly in the terminal after a natural-language
  description.
- Searching and browsing the public web for current technical information when
  local knowledge is insufficient.
- Reusing curated operational knowledge from previous Claude, Codex, ChatGPT,
  runbook, and on-call work.
- Presenting commands before execution and retaining command output for
  follow-up analysis.

The principal UX motivation for using Warp is not merely model access. It is
Warp's terminal interaction model: generated commands can be reviewed, executed
locally, and analysed in the same working surface.

The local machine has enough memory to run a materially stronger local model
than a 7B or 8B model. This allows MIMIR to use a capable local instruct,
reasoning, or agent-oriented model while keeping hosted coding systems focused
on implementation work.

-------------------------------------------------------------------------------

2. Decision
===========

MIMIR will be designed as a local-first, model-agnostic operations investigation
platform with:

- A local model runtime on the 128 GB Apple Silicon Mac.
- A LangGraph-based orchestration layer for stateful investigations.
- A council of specialist agents.
- Deterministic programmatic helpers for shell, repository, Kubernetes, SDM,
  container, database, and web workflows.
- A reusable skills system inspired by the Agent Skills approach used by Claude
  Code and supported by Kimi Code.
- Curated Markdown memory and runbook storage.
- Evidence-first answers with explicit distinction between observed facts,
  inferences, and unverified hypotheses.
- A CLI.
- A web UI backed by an API.
- Human approval gates for sensitive or mutating actions.
- An authenticated OpenAI-compatible API facade.
- A future HTTPS exposure path through Cloudflare Tunnel for Warp custom
  inference/BYOK use.

MIMIR will support two execution modes:

A. Standalone MIMIR Agent Mode
------------------------------
Used through the local CLI and web UI.

In this mode, MIMIR owns:

- Planning.
- Specialist delegation.
- Tool execution.
- Investigation state.
- Retrieval.
- Memory.
- Approval gates.
- Evidence assembly.
- Final synthesis.

B. Warp Inference Mode
----------------------
Used when Warp is configured with MIMIR's OpenAI-compatible HTTPS endpoint.

In this mode, Warp remains the outer terminal agent and MIMIR behaves primarily
as a compatible inference service. This avoids placing a full autonomous
LangGraph agent loop inside Warp's own agent loop by default.

The shared local model, memory, prompt assets, and selected read-only retrieval
capabilities may still improve model responses in Warp mode. More complex
MIMIR workflows should later be exposed to Warp as explicit specialist tools,
preferably through MCP or another supported local tool integration, rather than
silently nesting two competing agents.

3. Goals
========

3.1 Primary goals
-----------------

G1. Terminal command assistance
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
The user can describe an operational command in natural language and receive a
correctly formed command suitable for direct review and execution.

Examples of command families include:

- kubectl
- sdm
- psql
- shell tools
- log filtering
- container inspection
- Kannel-related operational commands
- Tankers-related operational commands

G2. Repository investigation
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
MIMIR can search one or more repositories to identify:

- Entry points.
- Call paths.
- Configuration.
- Tests.
- Feature flags.
- Failure handling.
- Timeout settings.
- Fallback behaviour.
- Relevant service boundaries.

Answers should cite exact files and line ranges wherever practical.

G3. Operational investigation
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
MIMIR can guide or execute read-oriented investigations using the user's local:

- VPN access.
- Internal DNS.
- kubeconfig.
- SDM authentication.
- Shell environment.
- Repository checkouts.
- Approved command-line tools.

G4. Log and timeout diagnosis
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
MIMIR can gather and correlate evidence to answer questions such as:

- Why is this service timing out?
- Is the timeout generated by the caller, callee, ingress, proxy, database, or
  another dependency?
- Are pods restarting?
- Is CPU throttling or memory pressure present?
- Is a connection pool saturated?
- Is there a retry amplification pattern?
- Does the repository configuration agree with the deployed state?

G5. Curated operational memory
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
MIMIR can retrieve relevant knowledge from curated Markdown files that contain:

- Runbooks.
- Service maps.
- Historical incident summaries.
- Command conventions.
- Environment conventions.
- Repository notes.
- Known failure patterns.
- Prior verified findings distilled from Claude, Codex, ChatGPT, or human work.

G6. Web research
~~~~~~~~~~~~~~~~
MIMIR can search and browse public web sources for current or niche technical
information, and it can cite the sources used.

G7. Multi-interface access
~~~~~~~~~~~~~~~~~~~~~~~~~~
MIMIR can be used through:

- A local CLI.
- A web UI/API.
- Eventually, Warp through an authenticated OpenAI-compatible HTTPS endpoint.

G8. Safe operational assistance
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
MIMIR separates investigation from mutation and requires approval before risky
actions.

3.2 Secondary goals
-------------------

- Reusable specialist workflows.
- Session persistence.
- Auditable command execution.
- Model portability.
- Local control over model weights and inference.
- Ability to benchmark multiple local models.
- Ability to hand off a compact evidence package to Claude or Codex for coding.

-------------------------------------------------------------------------------

4. Non-goals
============

The following are explicitly not primary goals for the initial system:

NG1. Autonomous software development
------------------------------------
MIMIR is not intended to replace the company's GLM/LiteLLM coding setup,
Claude, or Codex.

It may read code, search code, explain behaviour, and identify implementation
scope. It does not need autonomous file editing or code-writing tools in the
initial design.

NG2. Unsupervised production control
------------------------------------
MIMIR is not intended to make arbitrary production changes without explicit
human approval.

NG3. Secret management
----------------------
MIMIR is not a credential vault. It should use existing local authentication
systems such as SDM, kubeconfig, environment credential helpers, and OS-level
secret storage.

NG4. Raw conversation-history ingestion as trusted memory
---------------------------------------------------------
Raw Claude, Codex, or ChatGPT chats are not automatically treated as truth.
Useful material must be curated, dated, and preferably verified.

NG5. Public exposure of privileged tools
----------------------------------------
The public HTTPS endpoint intended for Warp inference must not directly expose
unrestricted shell, SDM, Kubernetes, database, or filesystem execution APIs.

NG6. Guaranteed parity with frontier hosted models
---------------------------------------------------
The local system is intended to be strong for the user's specific operational
environment. It is not assumed to outperform frontier hosted models on every
general reasoning task.

5. User-facing capabilities
===========================

5.1 Command completion and construction
---------------------------------------

The user should be able to enter requests such as:

- "Show pods in this namespace that restarted in the last hour."
- "Fetch logs for this deployment for the last 30 minutes and filter timeout
  errors."
- "Connect through SDM and inspect the relevant Kannel container."
- "Show the current memory requests and limits for this deployment."
- "Prepare a command to raise memory from 512Mi to 1Gi, but do not execute it."
- "Open psql through the approved SDM resource and show active connections."
- "Explain this command and its risks."

Expected behaviour:

1. Resolve missing context from the current terminal, stored profile, or user
   prompt.
2. Construct the command.
3. Display it before execution.
4. Explain target, scope, and risk when relevant.
5. Execute only after required approval.
6. Preserve command, output, exit code, timestamp, and environment metadata.
7. Allow follow-up questions using the output as evidence.

5.2 Repository search and behaviour verification
------------------------------------------------

Example request:

"Does this service fail open when the auth dependency times out?"

Expected workflow:

1. Identify repositories likely to contain the behaviour.
2. Search relevant symbols, strings, tests, configuration, and call sites.
3. Inspect candidate entry points.
4. Trace the path across files.
5. Inspect tests and deployment configuration.
6. Produce:
   - A direct conclusion.
   - Files and line ranges.
   - An ordered flow.
   - Supporting tests/configuration.
   - Unknowns or contradictory evidence.
   - Confidence level.

5.3 Cross-file flow tracing
---------------------------

MIMIR should support questions such as:

- Where does this inbound event enter the system?
- Which handler receives it?
- Which client or queue is called next?
- Where is state persisted?
- What happens on timeout?
- Which branch is selected by this flag?
- Which service owns the next step?

A flow result should use structured evidence rather than a prose-only summary.

5.4 Container and SDM investigation
-----------------------------------

MIMIR should be able to help with environments where access is mediated by SDM
and where Kannel or Tankers workloads run inside containers.

The exact SDM commands, resource naming, and access mechanisms are environment
specific and must be learned from approved local documentation and curated
skills. They are not invented in this ADR.

MIMIR should support a constrained workflow:

1. Identify or ask for the SDM resource.
2. Verify local SDM status.
3. Connect using the user's existing authenticated client.
4. Identify target container/service.
5. Run safe inspection commands.
6. Capture output.
7. Summarise evidence.
8. Propose further checks.
9. Pause before mutation.

5.5 Kubernetes investigation
----------------------------

Initial Kubernetes support should focus on read-oriented commands:

- get
- describe
- logs
- events
- top
- rollout status
- auth can-i
- config current-context
- targeted exec for inspection, subject to policy

Mutation-capable commands may be added behind approval:

- rollout restart
- scale
- patch
- set resources
- delete pod
- apply
- database writes triggered through container exec

MIMIR should always show:

- Cluster/context.
- Namespace.
- Target resource.
- Exact command.
- Expected impact.
- Risk classification.
- Rollback or recovery guidance when applicable.

5.6 Log analysis
----------------

MIMIR should:

- Accept pasted logs.
- Read output from commands it executed.
- Retrieve logs through kubectl or approved SDM/container workflows.
- Filter by time, service, pod, correlation ID, error class, or known patterns.
- Group repeated events.
- Correlate caller and callee timestamps.
- Separate symptoms from causes.
- Rank hypotheses.
- State what remains unverified.

5.7 Web search and browsing
---------------------------

MIMIR should support:

- Search-engine queries.
- Opening selected result pages.
- Extracting relevant text.
- Following links when necessary.
- Searching official documentation first for technical questions.
- Returning citations.
- Recording retrieval timestamp.
- Distinguishing web evidence from local environment evidence.

Web content is untrusted input and must not be allowed to inject tool
instructions or bypass local safety policies.

5.8 Evidence-package handoff
----------------------------

MIMIR should be able to produce a compact handoff for hosted coding tools:

- Problem statement.
- Observed behaviour.
- Evidence.
- Relevant file paths and line ranges.
- Commands executed.
- Relevant logs.
- Likely cause.
- Uncertainty.
- Suggested implementation scope.
- Explicit non-goals.

This package can be given to GLM, Claude, or Codex so those systems spend less
time rediscovering context and more time implementing the required change.

Responsibilities:

7. Council of Specialists
=========================

MIMIR will use a council pattern rather than one undifferentiated agent.

The council is not a group-chat gimmick. Each specialist should have:

- A narrowly defined responsibility.
- Restricted tool access.
- A structured output schema.
- Clear delegation criteria.
- A confidence field.
- Evidence requirements.
- A limited context relevant to its task.

7.1 Proposed specialist roles
-----------------------------

S1. Coordinator / Dispatcher
~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Classifies the request and selects the appropriate workflow.

It should determine whether the request is primarily:

- Command construction.
- Repository exploration.
- Feature verification.
- Kubernetes investigation.
- SDM/container investigation.
- Log diagnosis.
- Web research.
- Historical-memory lookup.
- Mutation planning.

S2. Repository Explorer
~~~~~~~~~~~~~~~~~~~~~~~
Read-only specialist for:

- File discovery.
- Keyword and symbol search.
- Import/call-path tracing.
- Test lookup.
- Configuration lookup.
- Service flow explanation.

It must not edit files.

S3. Behaviour Verifier
~~~~~~~~~~~~~~~~~~~~~~
Determines whether a claimed feature or behaviour exists.

It should require evidence from:

- Current code.
- Tests.
- Configuration.
- Deployment manifests.
- Relevant documentation.

S4. Kubernetes Investigator
~~~~~~~~~~~~~~~~~~~~~~~~~~~
Handles cluster inspection and command construction.

Initial bias: read-only.

S5. SDM / Container Investigator
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Handles approved workflows involving SDM-managed access, Kannel containers,
Tankers containers, and other environment-specific resources.

S6. Log and Timeout Analyst
~~~~~~~~~~~~~~~~~~~~~~~~~~~
Correlates logs and operational evidence, constructs hypotheses, and ranks likely
causes.

S7. Web Researcher
~~~~~~~~~~~~~~~~~~
Searches current public sources, browses selected pages, and returns cited
findings.

S8. Memory Curator
~~~~~~~~~~~~~~~~~~
Retrieves existing memory and proposes additions or updates after an
investigation.

It should not silently promote raw conclusions into trusted memory.

S9. Safety and Command Reviewer
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Classifies risk, validates target context, checks command shape, and determines
whether approval is required.

S10. Synthesis Specialist
~~~~~~~~~~~~~~~~~~~~~~~~~
Combines specialist outputs into a concise, evidence-backed final result.

7.2 Council decision pattern
----------------------------

For difficult investigations, MIMIR may ask multiple specialists to independently
analyse the same evidence.

A possible pattern:

1. Coordinator defines the question.
2. Repository Explorer gathers code/config evidence.
3. Kubernetes or SDM Investigator gathers live evidence.
4. Log Analyst forms operational hypotheses.
5. Behaviour Verifier checks whether conclusions are supported.
6. Safety Reviewer checks proposed commands.
7. Synthesis Specialist produces the final answer.

Disagreement must be visible. The system should not erase conflicting findings
merely to produce a neat answer.

8. Kimi-inspired three-helper pattern
=====================================

MIMIR should include a three-helper capability inspired by the Kimi Researcher
pattern, which uses three main tool classes: search, browser, and programmatic
execution.

These helpers are tools, not necessarily separate models.

K1. Parallel Search Helper
--------------------------
Purpose:

- Search many local or public sources efficiently.
- Run keyword and semantic searches in parallel.
- Search multiple repositories.
- Search runbooks and incident memory.
- Search web indexes.
- Return a compact ranked result set.

Examples:

- rg/git grep across repositories.
- Symbol search.
- Memory search.
- Web search.
- Log-index query adapters where available.

K2. Browser / Reader Helper
---------------------------
Purpose:

- Open selected documents or web pages.
- Extract relevant sections.
- Follow links.
- Preserve source metadata.
- Read local Markdown, source files, manifests, or documentation.
- Return only relevant excerpts to control context growth.

K3. Programmatic Execution Helper
---------------------------------
Purpose:

- Run deterministic code or commands to gather and transform evidence.
- Filter large outputs before sending them to the model.
- Group logs.
- Parse JSON/YAML.
- Compare manifests.
- Calculate summaries.
- Execute approved shell wrappers.
- Query structured systems through adapters.

This helper should reduce model round trips and context use by doing bulk
retrieval/filtering programmatically and returning compact results.

-------------------------------

A restricted code-runner may be used for:

10. Skills system
=================

10.1 Design basis
-----------------

MIMIR should adopt a reusable skills design inspired by the Agent Skills format
used by Claude Code and supported by Kimi Code.

A skill is a versioned package containing:

- A SKILL.md instruction file.
- Optional references.
- Optional scripts/helpers.
- Metadata.
- Tool permissions.
- Example inputs and outputs.
- Safety rules.
- Test cases.

10.2 Skill loading
------------------

Skills should use progressive disclosure:

1. The coordinator sees skill names and descriptions.
2. Relevant skill instructions are loaded only when selected.
3. References and scripts are loaded only when required.

This prevents every task from carrying every runbook and tool definition in the
model context.

10.3 Initial skill families
---------------------------

The exact content must be created from real operational knowledge.

Potential initial skills:

- kubernetes-readonly-investigation
- kubernetes-resource-review
- kubernetes-memory-change-plan
- pod-restart-investigation
- timeout-investigation
- sdm-resource-investigation
- kannel-container-investigation
- tankers-container-investigation
- psql-readonly-investigation
- repository-feature-verification
- repository-flow-tracing
- service-dependency-tracing
- web-technical-research
- incident-evidence-package
- historical-incident-comparison
- command-explainer
- safe-command-completion

10.4 Hooks
----------

MIMIR should support lifecycle hooks similar in purpose to Claude Code hooks:

- Before tool execution.
- After tool execution.
- Before mutation.
- After mutation.
- On approval request.
- On session completion.
- On memory-promotion request.
- On web content ingestion.

Hooks can:

- Reject prohibited commands.
- Validate cluster/namespace.
- Add audit metadata.
- Redact secrets.
- Trigger notifications.
- Run formatting or validation.
- Require an additional approval.

10.5 Subagent execution
-----------------------

Skills may run in a specialist subgraph rather than polluting the coordinator's
context.

For example:

- repository-flow-tracing runs in the Repository Explorer subgraph.
- timeout-investigation runs in the Log Analyst subgraph.
- web-technical-research runs in the Web Researcher subgraph.

11. Memory and knowledge
========================

11.1 Memory layers
------------------

MIMIR should separate four types of memory.

M1. Stable operational knowledge
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Examples:

- Service ownership.
- Repository mappings.
- Namespace conventions.
- SDM resource naming conventions.
- Common command forms.
- Environment topology.

M2. Runbooks
~~~~~~~~~~~~
Ordered, reviewed procedures for recurring investigations.

M3. Historical incidents
~~~~~~~~~~~~~~~~~~~~~~~~
Summaries of past incidents:

- Date.
- Symptoms.
- Evidence.
- Root cause.
- Resolution.
- Lessons.
- Applicability limits.

M4. Session memory
~~~~~~~~~~~~~~~~~~
Current investigation state:

- Commands run.
- Outputs.
- Evidence.
- Hypotheses.
- Rejected hypotheses.
- Pending checks.
- Approvals.
- User decisions.

11.3 Markdown metadata
----------------------

A memory document should support metadata such as:

- title
- category
- service
- environment
- created_at
- last_verified
- source
- confidence
- owner
- supersedes
- expires_after
- tags

11.4 Memory trust order
-----------------------

MIMIR should prefer evidence in this order:

1. Live command output.
2. Current repository/configuration.
3. Current deployment state.
4. Recently verified runbook.
5. Verified historical incident.
6. Curated imported memory.
7. General model knowledge.

11.5 Importing Claude/Codex/ChatGPT knowledge
---------------------------------------------

MIMIR may import or distill knowledge from prior tools, but:

- It must not assume access to private product memory APIs.
- Raw exports should be treated as untrusted source material.
- Candidate knowledge should be summarised.
- Secrets and sensitive data should be removed.
- Claims should be dated.
- Important claims should be verified against current code or systems.
- Conflicting memories should be retained as conflicts until resolved.

11.6 Memory promotion workflow
------------------------------

Suggested flow:

1. Session produces a candidate finding.
2. Memory Curator extracts a proposed note.
3. The note includes sources and verification status.
4. User reviews or approves it.
5. The note is stored in the appropriate layer.
6. Future retrieval respects freshness and verification status.

13. Safety model
================

13.1 Core rule
--------------

The model may propose actions. Deterministic policy code decides whether they
can run automatically.

13.2 Suggested risk classes
---------------------------

R0. Pure analysis
~~~~~~~~~~~~~~~~~
No execution.

Examples:

- Explain a command.
- Search memory.
- Analyse pasted logs.

R1. Read-only local
~~~~~~~~~~~~~~~~~~~
Examples:

- rg
- git grep
- reading files
- kubectl get
- kubectl describe
- kubectl logs
- kubectl events
- kubectl top
- SDM status/list commands

R2. Elevated inspection
~~~~~~~~~~~~~~~~~~~~~~~
Examples:

- kubectl exec for read-only inspection
- port forwarding
- opening a database session
- reading sensitive operational output

Requires confirmation or policy-based approval depending on context.

R3. Reversible mutation
~~~~~~~~~~~~~~~~~~~~~~~
Examples:

- rollout restart
- scale
- set resources
- patch
- delete a single pod
- controlled UPDATE

Requires explicit approval and an impact summary.

R4. High-risk mutation
~~~~~~~~~~~~~~~~~~~~~~
Examples:

- broad delete
- apply/replace affecting many resources
- destructive SQL
- schema changes
- node drain
- commands with unclear targets
- commands involving production and wildcards

Requires strong approval, preview, and where possible rollback/recovery guidance.

13.3 Required pre-execution display
-----------------------------------

Before a sensitive action, MIMIR should show:

- Exact command.
- Resolved executable.
- Current cluster/context.
- Namespace.
- SDM resource.
- Database.
- Target objects.
- Expected effect.
- Risk class.
- Reason for the action.
- Rollback/recovery plan if available.

13.4 Secret handling
--------------------

MIMIR should:

- Use environment credential providers.
- Avoid storing tokens in Markdown.
- Redact likely secrets from logs and session storage.
- Avoid sending sensitive data to web search.
- Keep privileged helper services bound to loopback.
- Separate public inference access from local privileged execution.

13.5 Prompt-injection resistance
--------------------------------

Repository files, logs, Markdown notes, and web pages are untrusted data.

They must not be able to:

- Redefine system policy.
- Approve a command.
- Grant new tools.
- Change risk classification.
- Exfiltrate secrets.
- Instruct MIMIR to ignore local rules.

16. Warp integration
====================

16.1 Target outcome
-------------------

MIMIR should eventually be selectable in Warp as a custom model using an
authenticated OpenAI-compatible HTTPS endpoint.

Expected configuration shape:

- Endpoint name: MIMIR
- Endpoint URL: https://<approved-host>/v1
- API key: MIMIR-generated or gateway-managed secret
- Model name: configured local model alias
- Model alias: MIMIR Local Ops

16.2 Network path
-----------------

The expected path is:

Warp -> Warp server-side inference path -> Cloudflare HTTPS endpoint
     -> Cloudflare Tunnel -> MIMIR on the local Mac -> local model runtime

16.3 Command execution
----------------------

Warp executes terminal commands in the local desktop environment. Therefore
commands can use:

- Local VPN.
- Internal DNS.
- kubeconfig.
- SDM authentication.
- Shell environment.
- Local repositories.

The inference endpoint only supplies model responses.

16.4 Avoiding double orchestration
----------------------------------

MIMIR's Warp-facing OpenAI-compatible endpoint should initially behave as a model
gateway, not a full standalone LangGraph agent.

Reason:

- Warp already owns the outer agent loop.
- A nested autonomous graph can duplicate planning.
- Tool schemas may conflict.
- Approvals may become ambiguous.
- Latency and context use may increase.
- The same command might be proposed or executed twice.

The preferred later extension is:

- Warp uses MIMIR for inference.
- MIMIR specialist workflows are exposed as explicit MCP tools or other
  Warp-supported tools.
- Privileged tools remain local.
- Warp invokes a specialist intentionally.

16.5 Cloudflare exposure
------------------------

Only the authenticated inference facade should be exposed.

The following should remain loopback-only unless a separate secure design is
approved:

- Generic shell execution.
- SDM execution.
- Kubernetes mutation.
- Database access.
- Repository filesystem access.
- LangGraph administrative APIs.

3. Prefer official/primary sources for technical claims.
4. Search in parallel when useful.

6. Extract only relevant sections.
7. Cross-check important claims.

- Copyright limits.

- A candidate skill update.
- A candidate runbook update.

Promotion requires review or verification.

24. Risks
=========

R1. Agent-inside-agent conflicts
--------------------------------
Putting a full LangGraph agent behind Warp's model endpoint can duplicate
planning and tool use.

Mitigation:
Use a thin inference mode for Warp and expose specialist workflows explicitly.

R2. Over-trusting memory
------------------------
Historical notes can become stale.

Mitigation:
Freshness metadata, verification dates, trust ordering, and live evidence.

R3. Unsafe command execution
----------------------------
The system touches production-adjacent tooling.

Mitigation:
Typed helpers, local policy enforcement, risk classification, approval gates,
context display, audit logs, and restricted credentials.

R4. Prompt injection
--------------------
Repositories, logs, and web pages may contain malicious instructions.

Mitigation:
Treat retrieved content as data, separate policy from context, and prohibit data
from granting permissions.

R5. Local-model quality
-----------------------
A local model may be weaker than frontier hosted models on novel incidents.

Mitigation:
Use deterministic tools, council verification, evidence requirements, model
benchmarking, and handoff to hosted tools when necessary.

R6. Latency
-----------
Large local models may be too slow for command completion.

Mitigation:
Route quick command tasks to a faster model and deep investigation to a larger
model if needed.

R7. Context explosion
---------------------
Logs, repositories, and web pages can exceed practical context.

Mitigation:
Programmatic filtering, targeted retrieval, progressive skill loading,
summaries, and source references.

R8. Public endpoint abuse
-------------------------
The Warp-facing endpoint is internet reachable.

Mitigation:
Strong authentication, Cloudflare protections, rate limiting, restricted
routes, no exposed privileged tools, and audit logs.

R9. Sensitive data leakage
--------------------------
Operational logs may contain confidential data.

Mitigation:
Local processing by default, redaction, explicit web boundary, and controlled
persistence.

R10. Complexity
---------------
The council, skills, memory, LangGraph, web, CLI, UI, Warp, and model runtime can
become an elaborate hobby project that never becomes useful.

Mitigation:
Deliver in phases, benchmark each addition, and reject components that do not
improve measured outcomes.

26. Consequences
================

Positive consequences
---------------------

- The local model handles repository and operational investigation load.
- Hosted coding agents receive better-defined tasks.
- Warp can provide the desired command-first terminal experience.
- Operational knowledge becomes reusable and searchable.
- Repeated on-call procedures become structured.
- Commands and evidence become auditable.
- The system is tailored to the user's actual environment.
- Local inference reduces dependence on separate API billing for investigation
  tasks.

Negative consequences
---------------------

- The system is operationally complex.
- The local Mac becomes infrastructure.
- Warp integration requires a public HTTPS path.

- Local model quality may not match hosted frontier models on novel problems.
- Safety engineering is mandatory before mutation support.
- Memories and runbooks require maintenance.
- Web retrieval introduces untrusted data.
- Multiple interfaces increase testing and maintenance work.

     Source: Anthropic documentation, "Create custom subagents."

     Claude Code can connect to tools and data sources through MCP.
     Source: Anthropic documentation, "Connect Claude Code to tools via MCP."

[S5] Anthropic Programmatic Tool Calling
     Programmatic tool calling allows code to invoke tools, filter results, and
     reduce model round trips and context usage.
     Source: Anthropic documentation, "Programmatic tool calling."

[S6] Kimi Researcher
     Kimi Researcher describes a three-tool pattern: parallel search, a
     text-based browser, and a coding/programmatic execution tool.

[S7] Kimi Code skills, agents, tools, and SDK
     Kimi Code supports Agent Skills, subagents, built-in tools, MCP servers,

[S8] LangGraph
     LangGraph provides durable execution, streaming, persistence, subgraphs,

     Source: LangChain documentation, LangGraph overview, persistence,
     subgraphs, and interrupts.

[S9] Warp custom inference
     Warp supports custom OpenAI-compatible inference endpoints, including
     LiteLLM-style endpoints, for local interactive agent use. The endpoint must
     be reachable by Warp's inference path. Cloud-agent runs have different
     limitations.
     Source: Warp documentation, custom inference/BYOK and pricing FAQ pages.

28. Final decision summary
==========================

MIMIR will be built as a local-first personal operations investigation platform
running on a 128 GB Apple Silicon Mac.

It will:

- Assist with terminal commands and command completion.
- Search repositories and trace flows.
- Verify features and behaviours with evidence.
- Investigate kubectl, SDM, Kannel, Tankers, containers, databases, and logs.
- Diagnose timeouts using live evidence and repository context.
- Search and browse the public web with citations.
- Use curated Markdown memory and reusable skills.
- Use a council of specialists.
- Include search, browser, and programmatic execution helpers inspired by Kimi.
- Use LangGraph for stateful standalone workflows.
- Run through both CLI and web.
- Require approval for risky actions.
- Eventually expose an authenticated OpenAI-compatible HTTPS endpoint so Warp
  can use the local model through custom BYOK/custom inference.
- Keep coding primarily with the existing GLM/LiteLLM, Claude, and Codex tools.

The first milestone is not the full council or mutation support. It is proving
that a local model can be served reliably, accepted by Warp, and provide useful
command completion and read-only investigation on the target Mac.
