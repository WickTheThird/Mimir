ADR-002: MIMIR — Autonomous Software Engineering Scope
=======================================================

Status
------
Proposed

Date
----
2026-07-28

Decision owners
---------------
Filip Bumbu

Supersedes
----------
ADR-001 section 4, NG1 (Autonomous software development). Every other non-goal
in ADR-001 remains in force, specifically NG2 (no unsupervised production
control), NG3 (not a credential vault), NG4 (raw conversation history is not
trusted memory), and NG5 (no privileged tools on the public endpoint).

Purpose of this ADR
-------------------
This ADR does one job: it records that MIMIR's scope has changed from a
read-only operations assistant to a system that may also write code, and it
defines the write surface and the safety assumptions that change follow.

It deliberately does not describe the organisational model, specialist
catalogue, routing strategy, or self-improvement loop. Those are separate
decisions and belong in later ADRs. Keeping this one narrow is the point:
ADR-001 NG1 was reversed by intent, not by drift, and the reversal should be
readable on its own.

-------------------------------------------------------------------------------

1. Context
==========

ADR-001 NG1 stated that MIMIR "does not need autonomous file editing or
code-writing tools in the initial design" and was not intended to replace the
existing GLM/LiteLLM, Claude, or Codex setup for implementation work.

The implementation built to ADR-001 honours that literally. There are no file
mutation tools of any kind. The tool registry contains read helpers for
repositories, Kubernetes, SDM, databases, logs, and the web, plus a sandboxed
code runner that cannot write to the working tree.

The intent has since changed. MIMIR is now to accept a request, design a
solution, implement it, verify it, review it, and deliver it. That is a
different system from the one ADR-001 describes, and it invalidates NG1
specifically.

-------------------------------------------------------------------------------

2. Decision
===========

MIMIR may write code, subject to the write surface defined in section 3 and the
safety assumptions in section 4.

The evidence-first principle from ADR-001 is unchanged and now extends to
implementation: a claim that a change works must be supported by an observed
test result, not by a model asserting it.

-------------------------------------------------------------------------------

3. Write surface
================

3.1 Isolation
-------------

Code changes are made in a git worktree created for the task, never in the
operator's working tree. This is the central constraint of this ADR.

It gives three properties for free:

- Every change is reversible by discarding the worktree.
- Every change is reviewable as a diff against a known base commit.
- A failed or abandoned task leaves the operator's checkout untouched.

3.2 What MIMIR may do
---------------------

Inside a task worktree:

- create, edit, and delete files
- create commits on a task branch
- run the repository's build, test, lint, and type-check commands

3.3 What MIMIR may not do without explicit approval
---------------------------------------------------

- write anywhere outside the task worktree
- push to any remote
- alter git history (rebase, amend, force push, filter-branch)
- delete or move a branch that MIMIR did not create
- modify CI configuration, deployment manifests, or dependency lock files
- add a new third-party dependency

3.4 What remains prohibited
---------------------------

- writing to the operator's working tree directly
- any push to a default branch
- any change to files outside a configured repository root
- credential material of any kind in a commit

-------------------------------------------------------------------------------

4. Safety assumptions that change
=================================

4.1 Running repository code is an escalation
--------------------------------------------

This is the assumption most easily missed. ADR-001's risk model classifies
commands by what they do to live systems. Running a repository's test suite does
not touch a live system, but it executes arbitrary code from that repository,
including any code MIMIR just wrote and anything a dependency's test fixtures
do.

Test execution is therefore treated as elevated inspection, not as a read. It
runs with the sandbox's scrubbed environment so it cannot reach the operator's
kubeconfig, SDM session, or cloud credentials, and it runs inside the task
worktree.

4.2 Risk classification for code mutation
-----------------------------------------

The existing R0 to R4 scale is retained and extended rather than replaced, so
one policy engine still decides everything.

| Action                                        | Class |
| --------------------------------------------- | ----- |
| Reading files, diffing, static analysis        | R1    |
| Writing files inside a task worktree           | R1    |
| Committing to a task branch                    | R1    |
| Running build, test, lint inside the worktree  | R2    |
| Writing outside the worktree                   | R3    |
| Adding a dependency, editing CI or manifests   | R3    |
| Any push, or any history rewrite               | R4    |

Writing inside an isolated worktree is R1 because it is reversible by
construction and touches nothing the operator depends on. The risk in code
generation is not the write; it is the merge, and the merge is a human decision.

4.3 The approval gate moves
---------------------------

Under ADR-001 the gate sits before a command touches a live system. It still
does. This ADR adds a second gate: the diff.

No change leaves a task worktree without the operator seeing the diff. That
review is the code-writing equivalent of the ADR-001 section 13.3
pre-execution display, and it is not optional.

4.4 What does not change
------------------------

The policy engine remains deterministic and never consults a model. Retrieved
content, including any code MIMIR reads, remains untrusted data that cannot
grant permissions. Privileged tools remain loopback-only. Secrets are still
redacted before storage or display.

-------------------------------------------------------------------------------

5. Measurement status
=====================

This section exists because the previous discussion nearly encoded an
unmeasured figure as an architectural assumption.

Observed status: no statistically meaningful accuracy benchmark for MIMIR
currently exists.

What exists today is:

- deterministic tests of the policy engine and risk classifier
- unit tests of components
- a small number of manually verified investigation sessions

Any figure describing MIMIR's accuracy, hallucination rate, or unsupported
claim rate is aspirational until the evaluation harness produces it
reproducibly. No design decision may cite such a figure as justification until
then.

The metric this project will use is the unsupported claim rate: the proportion
of claims reaching a final answer without supporting evidence. It is chosen over
"hallucination rate" because it is defined against the existing evidence model
and is therefore countable rather than judged.

-------------------------------------------------------------------------------

6. Explicitly not decided here
==============================

The following are acknowledged as intended direction but are not decided by this
ADR, and no implementation should assume them:

- the organisational model (departments, roles, task DAG)
- the specialist catalogue and its size
- model routing and per-role model assignment
- specialist performance statistics and staffing logic
- any self-improvement or organisational-optimisation loop

The last of these in particular introduces organisational learning, which is a
different class of decision and warrants its own ADR.

-------------------------------------------------------------------------------

7. Consequences
===============

Positive
--------

- Implementation work can be delegated to MIMIR with a reviewable diff.
- Worktree isolation makes every change reversible without a rollback plan.
- One risk model still covers both operational and code mutation.
- The reversal of NG1 is recorded, so the safety model's shape stays explicable.

Negative
--------

- A write surface exists where previously there was none, and it is the largest
  single increase in blast radius since the project began.
- Test execution runs untrusted repository code, which the sandbox mitigates but
  does not eliminate.
- Worktrees consume disk and require lifecycle management.
- Reviewing diffs is human work, and it becomes the throughput limit. That is
  the intended trade: a bottleneck at review is preferable to unreviewed merges.
